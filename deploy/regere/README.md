# regere environments with ikit

What replaces `yotta-infra/new-app-dev` (the app) and `yotta-infra/new-app-dev-platform` (its
platform), as two standalone ikit workloads per environment: they share no network, and the
app reaches the platform only through platform-gw. The same files bring up any number
of envs (dev, qa, stg, ...) on one Docker engine without names colliding.

| File | What it is |
|---|---|
| `registry.yaml` | Registry versions (spec revision `+spec.1`) whose databases, URLs and keys come from templates, resources and generated secrets. `ikit registry import deploy/regere/registry.yaml`. |
| `scripts/create-service-dbs.sh` | Library script: a role and database per service from its `DB_NAME`/`DB_USER`/`DB_PASSWORD`. A `post-data` hook on both workloads. |
| `scripts/seed-app.sh` | Library script: launchpad's service list (the platform services at `<gateway>/<slug>`), authrs tenants and admins, the core tenant. A `post-apply` hook on the app workload. |
| `env-up.sh` | Brings up one env: creates (or resets) the two workloads, adds the services, removes any `wl link` left on either workload, adds the hooks, publishes or routes, applies. |
| `mock-backends.sh` | Local S3 (RustFS) and SQS (ElasticMQ) for a mock run in a throwaway ikit home. |

## Naming

Everything derives from the workload name, which ikit makes unique in the org
(`wl-<org>-<env>-<nnn>`) and whose org prefix is unique on a shared target.

| Thing | Name | Example (platform `wl-regere-dev-002`) |
|---|---|---|
| Compose project, containers | `<wl>`, `<wl>-<svc>-<n>` | `wl-regere-dev-002-common-services-1` |
| Group networks, volumes | `<wl>_<group>`, `<wl>_<svc>_<vol>` | `wl-regere-dev-002_platform` |
| How the app reaches a platform service | platform-gw, `<gateway>/<slug>` with the apps' key | `http://172.17.0.1:10003/load-optimizer` (local), `https://gw.stg.regere.ai/load-optimizer` |
| Buckets, queues | `<wl>-<svc>-<need>[-suffix]` | `wl-regere-dev-002-simulation-service-jobs` |
| Databases, roles | `DB_NAME`, `DB_USER` per service, in the workload's own postgres | `load_optimizer`, `load_optimizer_app` |

The platform is standalone: the two workloads share no network, and platform-gw is the
only way in. `seed-platform-gw` (a `post-apply` hook on the platform) registers the
platform services in the gateway and issues one key for the apps, derived from the
platform's generated `APP_KEY_SEED` secret and usable only from `APP_ALLOWED_IPS`.
`env-up.sh` hands that key to launchpad (`PLATFORM_GW_API_KEY`, a secret) with the gateway
URL (`PLATFORM_GW_URL`), and `seed-app` registers the platform services in launchpad as
`<gateway>/<slug>`. launchpad sends the key only to URLs under the gateway. Sockudo is
reached directly (the gateway doesn't carry WebSockets). decision-hub runs in the app
workload (with RabbitMQ, its only user), so core reaches it as `http://decision-hub:8080`.
Inside a workload nothing is written down either: references such as
`service:decision-hub.internal_url` resolve to the workload's own services. A new env is `env-up.sh --env qa --target <target>`.

## What changed against yotta

| yotta | here |
|---|---|
| `pf-*` service keys kept as DNS aliases so `http://pf-decision-hub:8080` resolves | No shared network: the app calls the platform through platform-gw with its own key, limited to the app hosts' IPs |
| launchpad service rows seeded with `pf-*` and `workflow_engine` hostnames, bypassing the gateway | `seed-app` points them at `<gateway>/<slug>` (and repoints a restored database, since the seed upserts by slug) |
| platform-gw rows and keys entered by hand in its console | `seed-platform-gw` hook: the same slugs, timeouts and `strip_prefix`, upserted on every apply |
| Passwords and keys pasted into `app.env` / `data.env`, one in `init.sh` in plain text | Generated by ikit (`generate:`) and kept in the org's secret store |
| `create-db.sh` with a CSV of roles and passwords, run by hand | `create-service-dbs` as a `post-data` hook: databases exist before services start |
| Hand-made buckets and SQS queue, shared AWS keys | `needs:` per service; `ikit apply` creates them, per-service IAM keys on AWS |
| simulation service + 3 copy-pasted worker blocks | `simulation-worker` with `command` and `replicas: 3`, sharing the service's queue and database (`use:`) |
| sockudo `config.toml` mounted where the image never reads it (it listens on 6001 with a default app, so `/rt` and message-flow realtime were broken) | sockudo configured by env on 6002; key and secret generated; message-flow reads them from sockudo |
| `CORE_DECISION_HUB_TIMEOUT_SECS=150` | core default `DECISION_HUB_TIMEOUT_SECS=150` |
| authrs v0.1.11 with `KV_STORE_ENCRYPTION_KEY` | `authrs@0.1.11`, key generated (32 bytes, base64) |
| decision-hub `kaushik91/decision-hub` running, compose file asking for ghcr | `ghcr.io/regere-ai/decision-hub:latest` |
| decision-hub and RabbitMQ in the platform stack | both in the app workload, next to core and workflow-engine; the platform runs no broker |
| common-services `shm_size: 2gb`, `extra_hosts` host-gateway | `shm_size` in the spec; route hosts mapped to the host automatically |
| Caddy: `/ui/app1*` unstripped, `/rt/app/*` stripped, `/` redirected | a stripped `/rt` route; the UI at the root (`env-up.sh --public-url`) |
| client-ui-next (Next.js) at `/ui/app1` | dwigital-shell at the UI host's root (its links are root-absolute); launchpad on its own host (`env-up.sh --public-url … --api-url …`); dwigital-shell calls launchpad server-side over the workload network |
| redis on `0.0.0.0:6378`, postgres on the ZeroTier IP | nothing published except what browsers need (or what you publish on purpose) |

## Mock run (laptop, nothing outside it touched)

Uses a copy of the ikit home without a remote, so nothing is pushed to the team's state and
no AWS resource is created. Keep it out of `/tmp` (cleared on reboot, taking the generated
secrets with it), and never run a newer ikit build without `IKIT_HOME` set: opening the real
home migrates its schema, which the installed ikit then refuses to read.

```bash
cp -a ~/.ikit ~/.ikit-mock && rm ~/.ikit-mock/orgs/regere/remote.yaml
```

```bash
export IKIT_HOME=~/.ikit-mock
```

```bash
ikit registry import deploy/regere/registry.yaml
```

```bash
deploy/regere/mock-backends.sh up
```

```bash
eval "$(docker run --rm ghcr.io/regere-ai/message-flow:1.0.2 gen-vapid | sed 's/^MF_CHANNELS__PUSH__/export /')"
```

```bash
SMTP_PASS=not-real deploy/regere/env-up.sh --env dev --target laptop --app wl-regere-dev-001 --platform wl-regere-dev-002 --reset
```

What the mock run on the laptop showed (15 November 2026, decision-hub in the app workload):

- Platform: 12 containers, simulation-worker at 3 replicas, no broker; buckets and the
  `wl-regere-dev-002-simulation-service-jobs` queue (with its DLQ) created by apply; its four
  databases (`load_optimizer`, `message_flow`, `platform_gw`, `simulation`) and roles created
  post-data, before any service started.
- App: 9 containers including decision-hub and rabbitmq; `decision_hub` created post-data in
  the app's postgres; core reaches `http://decision-hub:8080` (200) and the platform's
  common-services, but not the platform's postgres; launchpad's rows point at the local
  decision-hub and at `wl-regere-dev-002-*` for platform services; tenants `builder` and
  `siemens_energy` seeded; the seeded admin logs in through authrs; the UI answers on
  `/ui/app1`.

Found on the way, outside ikit:

- **decision-hub never starts its RabbitMQ backend**, here and on yotta since 4 November:
  `config/default.toml` declares exchange `decision-hub` as `topic` (rule-events) and again
  as `fanout` (rule-invalidations), and RabbitMQ refuses the second. Fixed in
  [Regere-AI/decision-hub#5](https://github.com/Regere-AI/decision-hub/pull/5)
  (rule-invalidations gets `decision-hub.invalidations`); the ghcr image has it once that
  merges and builds.
- **After a host reboot**, Docker restarts every container at once, without compose's start
  order; decision-hub then fails to reach a broker that is still starting and does not retry.
  Same on yotta. decision-hub should retry the connection.
- ElasticMQ (the mock) keeps queues in memory; after a restart, `ikit apply` recreates them.

## The real cutover

The calls, as decided for the actual deployment:

- **Data: dump and restore, then reseed.** Users, tenants, workflows and rules live in the
  yotta databases (core 119 MB, workflow_engine 221 MB, decision_hub 203 MB), so a fresh seed
  would lose them. Dump each database on yotta, restore into the new workload's database with
  `--no-owner` (create-service-dbs has already made the database and role), then run the seed
  hook again: launchpad's upsert repoints every service row to the new hostnames.
  `platform_decision_hub` moves from yotta's platform postgres into the **app** workload's
  postgres (database `decision_hub`); the other `platform_*` databases go to the platform
  workload, the `siemens_energy_*` ones to the app workload.
- **Buckets: adopt the existing ones for this env only.** Before the first apply,
  `ikit res adopt <svc>.assets <bucket>` for core (`new-dev-assets-d1g3h62dzl6i`),
  common-services, message-flow, load-optimizer and simulation (`new-app-dev-*`), and the
  queue with `ikit res adopt simulation-service.jobs <queue url>`. Adopted resources are
  never deleted by ikit. Every later env gets its own, created by `apply`.
- **Secrets that cannot be generated** (SMTP password, VAPID pair) come from the env file you
  pass to `env-up.sh`; reuse yotta's VAPID pair so existing browser push subscriptions stay valid.
- **Keys that must not change**: `GW_SECURITY__ENCRYPTION_KEY`, `GW_SECURITY__KEY_PEPPER` and
  authrs's `KV_STORE_ENCRYPTION_KEY` encrypt data in the databases you restore. Set yotta's
  values with `ikit svc set <svc> --secret <VAR>` before the first apply instead of keeping
  the generated ones.

Order:

1. Release this ikit and have everyone on the org upgrade (the state schema moves to 0019), then
   `ikit registry import deploy/regere/registry.yaml` and `ikit script add deploy/regere/scripts/*.sh`.
2. `env-up.sh --env dev --target <new-server> --public-url https://launchpad-headless-dev.regere.ai --no-apply`
   (the DNS name moves at the end; until then use a temporary host).
3. Adopt the buckets and queue, set the carried-over keys (above).
4. `ikit apply` the platform, then the app (data comes up, databases are created, services start).
5. Stop writes on yotta (`docker compose stop` in both folders), dump the nine databases,
   restore them into the new postgres containers (decision_hub into the app's, above),
   `ikit hook run seed --wl <app>`.
6. Point `launchpad-headless-dev.regere.ai` at the new server; `ikit apply` the app again so
   Caddy gets the certificate.
